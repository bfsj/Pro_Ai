# Qwen3-0.6B 的 INT4 分组与裁剪

原始 INT4 将同一输出行中相邻的 128 个权重映射到 16 个等级。本次在同一检查点的 196 个投影层上试验组大小 128、64、32，每种各测开启和关闭裁剪。激活和动态 KV Cache 使用 BF16。

开启裁剪时，分别尝试保留原范围的 100%、95%、90% 或 85%。每个权重组独立选择重建均方误差最小的方案，计算误差时使用实际存储的 BF16 缩放和偏移。组变小可以更好地适应局部取值范围，但每组都要存自己的缩放和偏移。裁剪在打包前完成。

## 开发集选型

沿用此前 12 段文本，共 369 个受评 token。选型规则为设备上开发集困惑度最低的 INT4 配置。原 BF16 对照在 GPU 和 CPU 分别为 80.38 和 81.02。

| 组大小 | 裁剪 | 模型张量 MiB | RTX 4090 困惑度 | Xeon CPU 困惑度 |
|---:|---|---:|---:|---:|
| 128 | 关 | 520.00 | 151.67 | 150.51 |
| 128 | 开 | 520.00 | 140.75 | 140.46 |
| 64 | 关 | 533.13 | 115.37 | 115.20 |
| 64 | 开 | 533.13 | 116.70 | 118.50 |
| 32 | 关 | 559.38 | 103.84 | 104.69 |
| 32 | 开 | 559.38 | 99.35 | 99.50 |

两台设备都选中 32 加裁剪。组大小带来的改善最大。64 组虽然优化了局部权重误差，开启裁剪后的端到端困惑度反而略升。

## 固定配置后的验证

留出集为另外编写的 16 段中英文短文，共 665 个受评 token。各段独立分词，按 token 数加权汇总负对数似然再取指数。仅对 BF16、原 INT4 和开发集选出的配置评分。吞吐在 batch=1、输入 128、生成 32 token 的固定合成输入上预热后测三次，表中取中位数。显存指该生成负载下 PyTorch 分配的峰值，排除加载和打包阶段。

| 配置 | GPU 留出困惑度 | CPU 留出困惑度 | GPU tokens/s | CPU tokens/s | GPU 生成峰值 MiB |
|---|---:|---:|---:|---:|---:|
| BF16 | 58.62 | 58.69 | 36.99 | 7.78 | 1162.75 |
| INT4，128，关闭裁剪 | 105.04 | 104.18 | 37.15 | 12.50 | 550.38 |
| INT4，32，开启裁剪 | 72.38 | 72.64 | 37.59 | 12.24 | 591.25 |

这批短文支持用额外 39.38 MiB 模型存储换取更低困惑度。吞吐仅作单负载检查，更广泛的能力和硬件性能结论还需要公开语料、任务集与多负载重复测试。[GPU 逐段损失及原始计时](cuda.json) · [CPU 逐段损失及原始计时](cpu.json) · [留出文本](../../../scripts/quantization_holdout.txt)

## 复现

在已安装本项目的 PyTorch 2.11 环境运行。CPU 对照可将 device 换成 cpu。脚本在选型结束之后才对三种配置计算留出集分数。

```sh
python scripts/tune_int4.py --model "$MODEL" --device cuda --output tuning.json
python scripts/quantization_bench.py --model "$MODEL" --mode int4 --group-size 32 --mse-clip --device cuda --output benchmark.json
```

代码入口为 `quantize_decoder(model, group_size=32, mse_clip=True)`。不传新参数时沿用原始配置，便于复现实验。
